During workspace discovery I inadvertently opened `specs/r4_trials.md`, which contains summarized R6 outcomes; I did not use those values in this readiness assessment.

## Status

The governance-first template's synthetic end-to-end test passes: `python -m pytest r4_harness/tests/test_runner_template_e2e.py -q` returned **4 passed** (one unrelated pytest deprecation warning). The test creates disposable fixtures in pytest's temporary directory, exercises the real Newey–West, circular block bootstrap, DSR, Holm, preregistration, manifest and lock/result-writing helpers, and does not load market prices. The test establishes synthetic governance wiring; it does not validate a production data adapter or an S&P portfolio.

## S&P universe and benchmark fit

The template accepts an arbitrary `analyze(governance)` callback and an `expected_window`, so an S&P-specific adapter can be called after governance passes. The template has no explicit universe or benchmark fields. `phase3.portfolio_engine` constructs its benchmark as equal weight across all active rows in the supplied price arrays. Therefore, it can represent an equal-weight S&P benchmark only if the adapter supplies the point-in-time S&P constituent universe as the portfolio rows, with membership and prices aligned by date. A static current-constituent panel would not be an adequate S&P historical benchmark.

Before an authorized run, freeze and pass these values through the R7 config, manifest, and adapter:

- Universe identifier and source; point-in-time constituent roster by date; treatment of additions, removals, delistings, and missing prices.
- Benchmark identifier (`S&P 500 equal weight`), exact daily membership rule, return construction, reconstitution timing, and whether benchmark costs are charged under the agreed comparison convention.
- Input panel dimensions, asset/date ordering, adjusted-price fields and corporate-action policy, calendar, permitted date window, and data provenance.
- Signal and portfolio configuration: registered signal/version, long-only or long-short design, basket breadth, rebalance/fill dates, cost rate, and turnover calculation.
- Frozen preregistration path/hash; immutable run-lock, result and log paths; endpoint IDs and Holm-family manifest; cumulative trial count used for DSR.

The current helper does apply `cost_rate` to its internally constructed EW benchmark as well as to the strategy, and reports net excess and Sharpe ingredients. The adapter must confirm that this is the intended equal-weight benchmark convention. If the approved S&P benchmark requires a distinct price series, membership schedule, or methodology, the helper needs an explicit benchmark input or a separately validated benchmark calculation; do not silently approximate it with a different asset panel.

The current governance template is R6-shaped: preregistrations must live in `specs/r6_prereg`, the Holm loader validates the provided manifest, and trial counting searches the R6 variant section. An R7 runner must explicitly configure an R7 preregistration registry, R7 endpoint family that preserves the mandated prior family, and cumulative R7 trial accounting. Do not reuse R6 identifiers or use a narrow R7-only count for DSR. Freeze the cumulative DSR trial count and the full Holm family before any R7 outcomes are accessed.

## Pre-run checklist script specification

Implement a read-only preflight command (for example, `python report_drafts/r7_pre_run_check.py --config <frozen-config.json>`) that exits nonzero on any failed gate and prints a machine-readable JSON result plus a concise human summary. It must never load price arrays, calculate signals/returns, or write run outputs. Run it immediately before the separately authorized runner invocation.

Required checks, in order:

1. **Config and paths:** Resolve the project root and all referenced preregistration, manifest, price inputs, helper modules, endpoint-family registry, trial ledger, run directory and result/log paths. Require each required input/helper/registry to exist and be a regular file; require output parent directories to exist or be creatable under the approved output root. Reject paths outside approved roots and output paths that collide with inputs, each other, the run-lock directory, or existing immutable artifacts. Require distinct run, result, log and manifest paths and refuse any pre-existing result or lock.
2. **Unique outputs:** Check that the run identifier and every output destination are unused across the R7 run registry. Validate both canonical resolved paths and file hashes where relevant; fail closed on an existing result, lock, or mechanism artifact. Do not overwrite or auto-suffix a collision.
3. **Sealed-date access boundary:** Require the approved development window `2020-11-27` through `2026-10-30`; reject any manifest date bounds outside it, any pre-window date-stamped component, and any path component indicating `holdout`/`sealed_holdout`. Check every adapter input against an explicit allowlist derived from the manifest and scan its declared path/config references for unmanifested input paths. Execute the eventual runner in a restricted process/container that can read only allowlisted development files and code, with sealed-holdout roots denied at the filesystem boundary. A filename/date scan alone cannot prove that sealed files are unreadable; if the operating environment cannot enforce the deny boundary, block execution.
4. **Frozen preregistration hash:** Validate a single `FROZEN` date and canonical SHA-256, recompute the digest, compare to the reviewed expected digest in config, and require the file's bytes/hash to remain unchanged after preflight. Reject drafts or a freeze date later than the run authorization.
5. **Input manifest:** Validate schema, declared universe/benchmark, exact development window, minimum/maximum input dates, `holdout_loaded: false`, input file list, source/provenance, expected dimensions/ordering, and a SHA-256 for every listed input. Require nonempty, unique, existing input paths contained in the approved root and verify file bytes against each hash. Confirm manifest roster and coverage attestations without opening outcome arrays in the checklist.
6. **Real helper availability:** Import and record hashes/versions for the exact runner and inference helpers the adapter will call. Run the isolated synthetic e2e test and lightweight direct helper contract checks on synthetic arrays only (Newey–West, placebo statistic/p-value, block bootstrap, Holm correction, DSR and portfolio engine). Require the helpers to match the frozen configuration and expected return types. Do not invoke data builders or production analysis during this gate.
7. **Placebo interpretation:** Require the preregistration/config to name the placebo transformation, preserved network properties, statistic, sidedness, finite-sample correction and decision rule. For the usual network placebo where larger positive statistic is the hypothesized effect, interpret `(1 + count(placebo >= observed)) / (draws + 1)` as the upper-tail p-value; report the two-sided p-value separately where registered. State that a nonsignificant placebo alone does not prove network specificity: the observed effect must also exceed the registered placebo distribution and pass the registered signal gate. Reject ambiguous or post-result interpretation text.
8. **Holm family:** Verify the family manifest hash, unique endpoint identifiers, exact correspondence to preregistered confirmatory tests, and complete p-value slots including unrun endpoints. Preserve the already mandated prior family and append all R7 confirmatory tests prospectively; do not omit failed/unrun registered tests or create a new family after seeing outcomes. Confirm that endpoints map to the required test order and that all result p-values will be adjusted against the same frozen family.
9. **DSR trial count:** Compute the DSR count from the frozen cumulative trial ledger, including all prior searched/executed variants required by the R7 accounting rule and every R7 variant registered before execution. Require reconciliation with the shared 30-variant budget and prior search history; log the derivation and freeze the resulting integer in config. Reject zero, missing, or R7-only counts that discard prior trials. The current helper's R6 variant parser must not be treated as authoritative for R7 without an explicit validated adaptation.
10. **Order/authorization:** Confirm the runner will execute signal test, then placebo, then portfolio, stopping on the first failed gate; the candidate and benchmark were declared before testing; the one-shot authorization is present; and the output destinations still do not exist. Emit `READY` only if every gate passes. This check grants no authorization by itself.

## Limits and handoff

This review verifies a synthetic runner path only. No S&P portfolio was run and no claim is made that historical S&P constituents, delisting treatment, coverage, sealed holdout availability, or power requirements have passed the R7 universe gate. The current shared template is reusable as a governance skeleton, but R7 needs an explicit S&P-aware manifest/config and benchmark adapter plus R7-aware Holm and cumulative-trial wiring before it is execution-ready.
